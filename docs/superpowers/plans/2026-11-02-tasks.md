# Tasks Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Tasks module you can use every day (Open, Upcoming, Done, Detail, quick add, subtasks, AI), plus the Core pieces it needs: module-owned migrations, `deleteWith`, and operations that are tRPC endpoints, ⌘K actions and AI actions from one description.

**Architecture:** Operation descriptions, `Due` and form field specs live in `@dlh/core` (shared by app and server). `implementOperation`, `operationsRouter`, `ops.undo` and the AI operation adapter live in `@dlh/server`; the API derives module routers and AI runners from them. Modules own their tables through `drizzle-orm` and their own `drizzle/` folder, applied by the API after Core's. The desktop builds ⌘K rows, an argument step and generated forms from manifest operations. `modules/tasks` holds the table, operations, quick-add parser, screens and AI runners.

**Tech Stack:** TypeScript, Zod 4, tRPC 11, Drizzle + Postgres, Hono, React 19 + TanStack Query/Router, React Aria (`@dlh/ui`), `@internationalized/date` (time zones), `chrono-node`, `fractional-indexing`, Vitest, Playwright.

**Spec:** `docs/specs/tasks.md`

**Decisions made while planning**

- `ServerModule.migrations` is `true` (folder `modules/<id>/drizzle`), not a `URL`: `import.meta.url` moves when the API is bundled. The API resolves folders against `MIGRATIONS_ROOT` (default: the repo root). Update the spec's `migrations: new URL(...)` line in Task 1.
- `CoreDeps` gains `operations: Map<string, ImplementedOperation>` and `deleteWith: Map<string, DeleteWith>` (keyed by item type); `collectServerModules` returns both.
- Undo travels as `UndoToken = { record: unknown; created: string[] }`. The scoped writer records created item ids; `ops.undo` and `ai.undo` soft-delete `created` with the full writer, then call the operation's `undo`.
- AI reads use a new `aiResult` status `listed { requestId, heading, items }`, set when a runner has `list()`; Ask answers from the model are unchanged.
- Item fields filled by AI go through a new optional `AiRunner.resolve()`; an ambiguous match turns a Do into `suggested` with up to 3 options.
- Form fields are described by plain `FieldSpec`s computed in `@dlh/core` (`formFields`), so `@dlh/ui` renders forms without depending on Zod.
- `CommandItem.keepOpen` lets a row enter an argument step instead of closing the bar.
- No module contract-test helper exists; Task 2 adds `expectModuleWrites` to `@dlh/server/testing`.
- There is no shared module-phrasings test today; Task 13 adds one in `modules/tasks/test`.
- Tasks ships its own seed (12 tasks, 2 with subtasks, dates relative to now).

## Global Constraints

- Priority values `medium` (default) and `high`, ordered `medium < high`. Quick add: `p1` = High, `p2` = Medium (whole word, any case), a lone `!` = High. `p0`, `p3` are not parsed.
- Weeks start Monday. "Today" and day buckets use the IANA `timeZone` the app sends (`Intl.DateTimeFormat().resolvedOptions().timeZone`).
- `due_date` and `due_at` never both set; `due_tz` only with `due_at`.
- One level of subtasks shown; `create`/`addParent` refuse a parent that is a subtask and a child that has subtasks.
- Every write goes through Core's writer; a `tasks`-only change calls `updateItem` with no fields.
- Modules never import `@dlh/db`; module JSX uses layout classes only (`scripts/check-module-classes.ts`).
- AI: `breakDown` 3–7 titles; `planToday` context at most 60 tasks; `rewriteNotes` Suggest returns exactly 2 versions; at least 8 phrasings per Tasks AI action; 90% interpreter gate.
- Sync: a change on another device shows within 2 seconds.
- Copy (verbatim): "All subtasks done. Complete the task?" · "Subtasks can't have subtasks" · "Changed since" · "Nothing open. Add one above" · "Nothing done yet" · "Today is clear" · "Type a date" · "Add a title" · "Today is \<Mon, Nov 2, 2026> (\<zone>)".

## Review Focus

1. **Dragging a timed task to another day in Upcoming.** It keeps its time of day in your zone and only the date changes. Test: Task 12 `moveToDay keeps the local time`.
2. **The week the clocks change** (Nov 1, 2026; Mar 8, 2027 in the US). Week bounds are seven local days and no task falls between them. Test: Task 5 `week bounds across DST`.
3. **Undo after the task changed elsewhere.** Nothing is reverted; `CONFLICT` "Changed since". Test: Task 4 `undo after a later edit conflicts`.
4. **Quick add with only a date** ("tomorrow 9am"). Nothing is created; the row says "Add a title". Test: Task 5 `date only leaves an empty title`, Task 9 `create row not ready without a title`.
5. **Ticking a task twice quickly** (double click, or a second device already ticked it). The second `complete` returns the task unchanged, without a write or a conflict. Test: Task 6 `complete twice is a no-op`.
